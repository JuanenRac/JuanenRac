Electro Hobby 3D is four independent engineering ecosystems by the same author: HYDRA-UMC (industrial multi-robot platform), URTC (its universal robot-tool subsystem, an independent product with its own firmware), A.R.M.O.R. (perimeter security and home automation) and EH3D (a PCB, CNC and laser fabrication suite). This dashboard discovers and lists every one of them live; each ecosystem's own family groups are labeled below, and HYDRA-UMC's own deeper architecture is detailed in the section right after this one.

HYDRA-UMC: System architecture

Platform foundation

Raspberry Pi OS ARM64 remains the operating-system base. The HYDRA-UMC layer adds device profiles, diagnostics and service lifecycle.

  • HYDRA-UMC-OS
  • CM5 / Linux
  • systemd / udev
  • MCU / URTC boundary

Contracts and operations

The SDK defines stable data and command contracts; Server, UI and tools use those contracts instead of raw hardware protocols.

  • HYDRA-UMC-SDK
  • Server / Studio / Suite
  • DSI / mobile / CLI
  • Job Dispatcher

Perception and intelligence

Vision and AI are optional capabilities. Their output is validated before it can influence a mission; they are never safety authority.

  • Vision Streamer / Node
  • Detection HEF
  • Cognitive / VLA
  • Safety Zones

Engineering and industry

Simulation, telemetry and standards make the physical cell observable, testable and interoperable.

  • Twin / Physics / HIL
  • Telemetry / DataLake
  • OPC-UA / MQTT
  • MTConnect / Gateway

Contracts and tests

HYDRA-UMC-SDK holds the v1 JSON Schemas, a Python reference validator, Go, TypeScript and Rust clients that enforce them, conformance fixtures, an OpenAPI slice of the server and a job intake that never runs the same idempotency key twice; a compatibility matrix and a differential test keep validator and schemas in step.

  • HYDRA-UMC-SDK
  • JSON Schema / OpenAPI
  • Go / TypeScript / Rust clients
  • Job intake

Verified updates

HYDRA-UMC-UPDATER installs and updates a repository by cloning, staging, verifying and only then promoting it, so a failed check leaves the live copy untouched; an optional gate refuses a commit without a trusted signature before anything is built. Firmware images are checked with CRC32 and a shared-key HMAC-SHA256; an asymmetric signature is planned, not implemented.

  • HYDRA-UMC-UPDATER
  • Staged install
  • Signed-commit gate
  • CRC32 + HMAC-SHA256
Operator interfaces→Server and SDK→CM5-MCU adapter→MCU / URTC / machine
HYDRA-UMC and URTC: HYDRA-UMC is the platform and cell controller. URTC is its universal robot-tool subsystem, with independent firmware and maintenance tools. The MCU remains authoritative for physical limits and safe stop; UI, network and AI cannot bypass that boundary.
URTC: System architecture

Tool-head firmware

An STM32F303 runs each tool head over CAN, reading its own 5-bit hardware address to auto-configure power stages, sensors and safety logic for one of 25 built-in tool profiles.

  • STM32F303
  • CAN bus
  • 5-bit ID matrix
  • 25 tool profiles

Expansion and motion

A 20-pin expansion connector adds a second stepper axis or sensor board through one of six interchangeable variants, sharing STEP/DIR/EN wiring between a TMC2209 and a TMC5160 driver.

  • TMC2209 / TMC5160
  • 6 expansion boards
  • F-RAM persistence
  • OLED diagnostics

Maintenance tools

URTC-FLASHER updates firmware over CAN without removing the board, URTC-TESTER exercises the protocol end to end and URTC-UPDATER keeps every desktop tool current from GitHub.

  • URTC-FLASHER
  • URTC-TESTER
  • URTC-UPDATER
  • CAN-OTA

Vision and operation

URTC-VISION-TOOL adds camera-based tool inspection, URTC-WEB-STUDIO gives it a browser console and URTC-SMART-RACK stores and identifies tool heads between changes.

  • URTC-VISION-TOOL
  • URTC-WEB-STUDIO
  • URTC-SMART-RACK

Contracts and tests

URTC-COMMON writes the CAN protocol once as data, generates a C header, TypeScript and Python modules and a protocol table from it, and keeps the conformance vectors every implementation must reproduce. The firmware and the desktop tools still keep their own copies until each one migrates, so today it is compared against them rather than used by them.

  • URTC-COMMON
  • CAN spec + generators
  • Conformance vectors
  • Migration plan

Release assets and signing

Each firmware release is published as GitHub release assets with SHA-256 sidecars and a manifest, and the release tool refuses to publish images signed with the public development key as an official release. The bootloaders check CRC32 and a shared-key HMAC-SHA256; asymmetric signatures are planned, and nothing has been flashed to a real board yet.

  • GitHub release assets
  • SHA-256 + manifest
  • Dev-key release gate
  • Asymmetric signing planned
Tool head→STM32F303 firmware→CAN bus→HYDRA-UMC MCU / host
URTC on its own, and paired with HYDRA-UMC: URTC is an independent, unofficial project - a CAN-based tool-head controller built to work with PAROL6/Faze4-style arms, with its own firmware, hardware and maintenance tools. When it is the tool subsystem of a HYDRA-UMC cell, HYDRA-UMC's own MCU keeps authority over physical limits and safe stop; URTC never bypasses that boundary.
A.R.M.O.R.: System architecture

Network segmentation

Field nodes and cameras sit on their own VLAN with no internet access; the MQTT broker and server live on a core VLAN; Studio and the Android app reach the server from a client VLAN.

  • VLAN 10 field
  • VLAN 20 core
  • VLAN 30 clients
  • MQTT, one identity per node

Field nodes

ESP32-S3 radar, solar, electrical, alarm and wall-panel nodes publish sensor and equipment readings or their state; the solar and electrical ones only read, never write to an inverter, battery or meter.

  • ARMOR-RADAR
  • ARMOR-SOLAR
  • ARMOR-ELECTRICAL
  • ARMOR-ALARM
  • ARMOR-HMI

Perception, never authority

Visual and voice AI recommend a severity or an intent with reasons attached; authorizes_action is always false until the server itself authenticates and confirms.

  • ARMOR-SERVER-AI
  • ARMOR-VOICE-AI
  • Recommend, never act

State and operator consoles

ARMOR-SERVER is the only place that ever touches a camera password or an RTSP address; Studio and the Android app are its authenticated clients, and a phone can set a new node up over Bluetooth alone.

  • ARMOR-SERVER
  • ARMOR-STUDIO
  • ARMOR-ANDROID-CONTROL
  • ARMOR-HMI
  • BLE set-up only

Contracts and tests

ARMOR-COMMON defines every node message once as a JSON Schema, with a validator that refuses what it does not implement, accepted and rejected conformance vectors that each implementation must pass, the OpenAPI file of the server's routes and the firmware base shared by the five nodes, which a tool keeps identical in each of them.

  • ARMOR-COMMON
  • JSON Schema / OpenAPI
  • Conformance vectors
  • Shared firmware base

Signed releases and updates

Node firmware is published with a SHA-256 and an Ed25519 signature, and both a node and ARMOR-SERVER refuse a release without a valid one. The maintenance helper of ARMOR-DEVOPS checks an Ed25519 signature on each service package before unpacking it, which is how ARMOR-STUDIO updates the central machine; the private key never goes to GitHub. A firmware file uploaded by hand is not checked.

  • Ed25519 firmware signatures
  • ARMOR-DEVOPS signed packages
  • ARMOR-STUDIO
  • Key never on GitHub
Field nodes and cameras→MQTT broker and server→AI recommendation→Authenticated client session
A.R.M.O.R.'s own boundary: The server is the only component that authorises an action or holds a camera credential. Visual and voice AI only recommend; solar and electrical nodes only read - the rules for switching an electrical source are tested in software but not yet linked to any real hardware.
EH3D: System architecture

One project file

EH3D-COMMON defines the .eh3dproj container: a ZIP archive with the project, its layers, toolpaths and vision data, a SHA-256 for every entry and limits that refuse unsafe or oversized names.

  • EH3D-COMMON
  • .eh3dproj
  • SHA-256 integrity
  • Machine telemetry types

Parsers and geometry

EH3D-CORE-LIBS reads Gerber RS-274X, Excellon drill files and G-code and recovers from damaged files with a diagnostic for every problem; HP-GL and 2D offsets follow.

  • EH3D-CORE-LIBS
  • Gerber RS-274X
  • Excellon
  • G-code

CAM tools

ISOCAM, DRILLPRO, ROUTEPRO, STENCILCAM, LASER-CAM and AUTOLEVEL turn PCB layers and images into isolation, drilling, contour, stencil, laser and height-compensated toolpaths.

  • EH3D-ISOCAM
  • EH3D-DRILLPRO
  • EH3D-ROUTEPRO
  • EH3D-LASER-CAM

Machine control

EH3D-MOTIONCNC streams G-code to the machine and EH3D-PENDANT-GUI jogs it from a touchscreen, with EH3D-CAM-DEBUGGER simulating every path first.

  • EH3D-MOTIONCNC
  • EH3D-PENDANT-GUI
  • EH3D-CAM-DEBUGGER
  • Simulator first

Assembly and vision

EH3D-PNP-MANAGER reads the centroid files for guided or automatic placement and EH3D-VISION-STUDIO aligns cameras and trains fiducials with the vision of HYDRA-UMC.

  • EH3D-PNP-MANAGER
  • EH3D-VISION-STUDIO
  • HYDRA-UMC vision link

One suite, one tool crib

EH3D-SUITE-LAUNCHER opens the tools, EH3D-TOOL-MANAGER keeps bits, wear and feeds in one database, EH3D-UPDATER keeps every repository current and EH3D-DOCS holds the manuals.

  • EH3D-SUITE-LAUNCHER
  • EH3D-TOOL-MANAGER
  • EH3D-UPDATER
  • EH3D-DOCS
Gerber, Excellon and images→Parsers and CAM tools→G-code and simulation→Machine
EH3D's honest state: EH3D is the newest ecosystem. Only EH3D-COMMON (the project container and the machine types) exists as published code so far, the parsers of EH3D-CORE-LIBS are being written and every other repository of the suite is planned. Nothing here has run on a machine yet, and the link with the vision of HYDRA-UMC is a plan, not a feature.

Roadmap

Not a feature timeline with dates - the real path every project in this ecosystem follows, and exactly where each one sits on it right now (see the Maturity section above for the live counts).

  1. Scaffolding 21

    A real, compilable entry point exists; the feature the project exists for does not yet.

    Advances once real, tested business logic exists behind it: its own test suite, a real end-to-end smoke test, or a real protocol round-trip - never a mock standing in forever.

  2. Functional 61

    Real, tested business logic - verified this pass (own test suite / real end-to-end smoke test / a real compiled protocol round-trip).

    Advances once a real consumer outside its own checkout - another real service, or a package actually installed rather than left editable - depends on it and proves that in a repeatable test, not just its own CLI or fixtures.

  3. Established 18

    A real, substantial version history under this ecosystem's own odometer scheme, AND real, sustained use beyond a passing test suite - deployed and actually operating, or genuinely depended on by other real projects. Trusted on that record, not re-audited this pass.

    Advances only once real, physical hardware exists for it to run against - the exact board or machine this ecosystem's own hardware documentation describes.

  4. Production 0

    Real firmware for a real, physical PCB this ecosystem's own hardware docs describe.

    The top of the ladder. Nothing advances past here - it just keeps shipping real fixes.
